# Plan: native AWS SSM Session Manager connection for krikri (issue #1664)

Status: in progress - phases 1-8 of section 7 implemented (codec/UUID, fake
gateway+agent+pty harness, control plane, session core, KMS encryption, the
standard credential chain, live validation against a real account, and the
krikri SSM transport: connection types, settings, registry, marker shell,
streamed/compressed transfers, typed errors, real-pty tests). Phase 9 (krikri
wiring) is next. Shard and krikri specs, `crystal tool format` and ameba are
green.
Scope owner: krikri-playbook (`~/git_work/krikri`) + new shard `krikri-aws-ssm`
Decision summary: fully native SSM client (no AWS CLI, no `session-manager-plugin`), implemented as a
separate MIT-licensed Crystal shard, with KMS session encryption, and full unit/integration/live tests.

---

## 1. Goal

`krikri-playbook -i <inventory with EC2 instance IDs> -e ansible_connection=amazon.aws.aws_ssm playbook.yml`
must behave like `ansible-playbook` with the same arguments, without an S3 bucket, without the AWS CLI
and without `session-manager-plugin` on the controller.

Required behaviour:

- target an EC2 instance by instance ID (`ansible_aws_ssm_instance_id`, else `ansible_host`, else host name);
- AWS credential chain: env vars, shared profile files, SSO cache, IMDSv2, ECS/IRSA, `credential_process`;
- region/profile/timeout options with Ansible's option names and precedence;
- file + module transfer over the session itself (base64 in both directions), never S3;
- `become`, `delegate_to`, check mode, `--diff`, loops, handlers, batching, gather_facts;
- KMS-encrypted sessions (accounts whose Session Manager preferences mandate encryption must work);
- parity-grade error/unreachable reporting.

Non-goals (documented in `KNOWN_MISSING.md`):

- Windows/powershell sessions (krikri has no winrm/psrp either);
- port forwarding and smux (`AWS-StartPortForwardingSession*`);
- `AWS-StartSSHSession` SSH-over-SSM tunnelling (would re-add the key distribution the issue rejects);
- S3 staging even when `ansible_aws_ssm_bucket_name` is set (warn once, ignore; krikri never needs it);
- `async:` tasks over SSM in v1: they fail cleanly with a documented message; support is a follow-up
  issue (section 14).

---

## 2. Why native + why a shard

Findings that drive the design (verified during review):

- AWS documents only the control plane (`StartSession` / `ResumeSession` / `TerminateSession`, and the
  `StreamUrl` + `TokenValue` semantics). The data-channel wire format is defined only by the
  Apache-2.0 reference implementations (`aws/session-manager-plugin`, `aws/amazon-ssm-agent`).
- It has nonetheless been fully documented by observation and reimplemented at least three times:
  - `hupe1980/aws-ssm-bridge` (MIT, Rust + Python): published "Wire protocol" doc covering the
    120-byte header, MessageId byte order, acks/retransmit, chunking, liveness, smux, KMS. Verified
    against a live agent 3.3.3572.0; fuzzes its parsers.
  - `dacort/pyssm-client` (Apache-2.0, Python): same binary protocol; its `copy` subcommand already
    does base64 file transfer over the session (the mechanism this issue asks for).
  - Metasploit's `lib/rex/proto/http/web_socket/amazon_ssm.rb` (independent implementation).
- Crystal is sufficient with no new runtime dependencies:
  - `HTTP::WebSocket` (stdlib) supports `wss:`, custom headers, binary frames, ping/pong callbacks
    (`/usr/share/crystal/src/http/web_socket.cr`); SSM uses no websocket subprotocol.
  - `OpenSSL::Cipher` has GCM (`gcm_tag`, `gcm_tag=`) for KMS session encryption.
  - `krikri-aws-signer` already does header-based SigV4 for arbitrary services, which is what the
    websocket upgrade needs. A presigned `StreamUrl` must be detected (`X-Amz-Signature` /
    `X-Amz-Credential` / ... query params) and dialed unsigned, exactly like the reference plugin's
    `IsPresignedURL`, and all URLs/tokens must be redacted in logs.
- Licensing: MIT (bridge), Apache-2.0 (plugin, pyssm-client) are all compatible with GPL-3.0-or-later
  krikri. Ship the shard MIT (matching `krikri-aws-signer`) with an honest `NOTICE` naming the
  sources the protocol was learned from. Do **not** claim clean-room.

Shard rationale: the SSM client is a protocol implementation with no Ansible semantics. It has its own
test suite, fake-agent harness and live opt-in validation; keeping it out of krikri keeps the
GPL shard thin, matches the existing `krikri-aws-signer` / `krikri-jinja` pattern (tag pin +
`shards update`), and lets the krikri-side work (marker shell, transfers, dispatch) iterate separately.

### 5.2 Public API

```crystal
module KrikriAwsSsm
  struct Credentials
    getter access_key : String
    getter secret_key : String
    getter session_token : String?
    getter expires_at : Time?
  end

  class CredentialChain
    def self.default : CredentialChain          # env, profile, sso, imds, ecs, web identity, process
    def resolve(profile : String? = nil) : Credentials
    def refresh(creds : Credentials) : Credentials
  end

  struct Settings
    property target : String
    property region : String                    # default "us-east-1" (Ansible parity)
    property profile : String?
    property endpoint_url : String?             # ssm control plane only; gateway URL comes from AWS
    property document : String?                 # nil = account default shell document
    property parameters : Hash(String, String)
    property connect_timeout : Time::Span       # ansible_aws_ssm_timeout (60s)
    property retries : Int32                    # ansible_aws_ssm_retries (3)
  end

  enum Stream; Stdout; Stderr; end
  record Output, stream : Stream, bytes : Bytes

  enum CloseReason; Clean; AgentClosed; NetworkLost; SessionTimeout; ProtocolError; Terminated; end

  class Session
    def self.open(settings : Settings, chain : CredentialChain = CredentialChain.default) : Session
    def write(bytes : Bytes) : Nil              # chunked input_stream_data
    def read? : Output?                         # ordered stdout/stderr bytes, nil at close
    def closed? : Bool
    def close_reason : CloseReason?
    def exit_code : Int32?                      # payload ExitCode
    def terminate : Nil                         # ssm:TerminateSession, idempotent
    def resume : Nil                            # ssm:ResumeSession + redial (same session/process)
  end
end
```

Concurrency contract: one writer (mutex-protected), one reader pump; `read?` returns nil once the
session is closed; `terminate` is idempotent and unblocks a blocked `read?`; a write after close
raises `ChannelClosed`. Anything a fake gateway needs (codec, payload structs, `Credentials`) is
public, and the fake gateway/agent/pty harness ships under `src/krikri_aws_ssm/testing/` (not `spec/`)
so krikri's integration tests can require it without cross-repo spec paths.

### 5.3 Wire protocol implementation detail

All integers big-endian. Header is 120 bytes, then payload.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 4 | HeaderLength | always 116 (excludes this field) |
| 4 | 32 | MessageType | ASCII, space-padded |
| 36 | 4 | SchemaVersion | always 1 |
| 40 | 8 | CreatedDate | Unix ms |
| 48 | 8 | SequenceNumber | per direction, starts 0 |
| 56 | 8 | Flags | SYN = 1, FIN = 2 |
| 64 | 16 | MessageId | UUID, **LSB half first** (Java `UUID` order) |
| 80 | 32 | PayloadDigest | SHA-256 of the payload as sent (post-encryption) |
| 112 | 4 | PayloadType | see below |
| 116 | 4 | PayloadLength | |
| 120 | n | Payload | |

Traps to pin with tests:

- **MessageId byte order**: agent stores UUIDs as two longs, least-significant half first. Wrong
  order = agent never matches our acks, retransmits forever, session hangs silently. `spec/uuid_spec.cr`
  pins encode and decode with hand-written bytes.
- **PayloadDigest** verified on receive; zero-length payloads and `start_publication` /
  `pause_publication` are exempt (matching the reference plugin).
- **Ack header**: `SequenceNumber = 0`, `Flags = SYN | FIN`; the acknowledged sequence lives in the
  JSON payload.
- **Inbound ordering**: `seq == expected` -> deliver + ack; `seq > expected` -> buffer + ack; `seq <
  expected` -> drop without ack (double-acking confuses the agent's buffer accounting).
- **Outbound**: single sequence counter shared by input data, terminal-size updates, handshake
  response and encryption challenge response, allocated under one mutex together with enqueueing.
  Only the queue head is retransmitted.
- **Chunking**: 1024-byte default input payload (`config.StreamDataPayloadSize`), configurable.
- **Liveness**: ping every 30s, idle deadline on any inbound frame (bridge's improvement over the
  plugin's 5-minute fire-and-forget ping), default idle timeout 120s.
- **Timers**: retransmit scan 100ms, initial RTO 200ms, Jacobson/Karels with 50ms..30s clamp, give up
  after 3000 attempts, buffer 10k each way.
- **pause_publication / start_publication**: stop/resume outbound sending (bounded queue; refuse new
  writes with backpressure rather than dropping the head).

Message types: `input_stream_data` (client->agent), `output_stream_data` (agent->client),
`acknowledge` (both), `channel_closed`, `start_publication`, `pause_publication`.

Payload types: 0 Undefined, 1 Output, 2 Error, 3 Size, 4 Parameter, 5 HandshakeRequest,
6 HandshakeResponse, 7 HandshakeComplete, 8 EncChallengeRequest, 9 EncChallengeResponse, 10 Flag,
11 StdErr, 12 ExitCode. Payload types 1, 11, 12 are encrypted when KMS is on; handshake/control
stay clear.

Session open sequence:

1. `ssm:StartSession` (signed JSON 1.1) -> `SessionId`, `StreamUrl`, `TokenValue`.
2. Websocket upgrade to `StreamUrl`, SigV4-signed over `ssmmessages` (GET, empty payload hash,
   `add_sha: false`). Do the upgrade **manually** as the primary path: open TLS (or plain TCP for a
   test endpoint), send the signed `HTTP::Request`/101 handshake ourselves, then wrap the socket in
   `HTTP::WebSocket.new(io)`. Reason: Crystal's `HTTP::WebSocket::Protocol.new` rewrites
   `headers["Host"] = "#{host}:#{port}"` (`/usr/share/crystal/src/http/web_socket/protocol.cr:334`),
   appending `:443`; SigV4 must cover the exact Host value that is sent. Manual upgrade also keeps
   `Sec-WebSocket-*` out of `SignedHeaders` and gives one place to redact the URL. If a presigned
   `StreamUrl` is detected, skip signing and dial it as-is. `wss://` in production; `ws://` only when
   an explicit test endpoint is configured. TLS context injectable (`AWS_CA_BUNDLE` if cheap).
3. Send TEXT frame: `{"MessageSchemaVersion":"1.0","RequestId":<uuid>,"TokenValue":...,
   "ClientId":<uuid>,"ClientVersion":"1.0.0"}`.
4. Agent sends `HandshakeRequest` (payload type 5, JSON) with `AgentVersion` and
   `RequestedClientActions`.
5. Reply `HandshakeResponse` (payload type 6): `ClientVersion`, `ProcessedClientActions`
   (`SessionType` -> Success; `KMSEncryption` -> see 5.5; unknown -> Unsupported + error).
6. Agent sends `HandshakeComplete` (payload type 7). Session ready; shell output begins.

Additional protocol notes:

- Header constants, `MessageType` padding, digest exemptions and ack flags are to be pinned from
  `clientmessage.go`/`messageparser.go` during phase 1, not just from the bridge doc.
- Payload type 3 (`Size`, cols/rows): decide send-vs-ignore (the pty has a size or it does not) and
  document the decision in `docs/protocol.md`.
- `ResumeSession` returns a fresh `StreamUrl`/`TokenValue` for the **same** session; pin from the
  plugin's `Reconnect` whether the open message, handshake and KMS state must be redone, rather than
  assuming the shell survives a redial.

### 5.4 Credential chain

AWS SDK precedence, implemented provider-by-provider with an expiry-aware cache:

1. `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` (+ `AWS_SESSION_TOKEN`).
2. `AWS_PROFILE` / `AWS_DEFAULT_PROFILE`, or `default`; parse `AWS_SHARED_CREDENTIALS_FILE`
   (`~/.aws/credentials`) and `AWS_CONFIG_FILE` (`~/.aws/config`).
   - `credential_process` (spawn, JSON out) - opt-in, documented as executing a configured command;
   - `role_arn` + `source_profile` -> STS `AssumeRole` (optional `role_session_name`,
     `external_id`, `duration_seconds`); chained roles (a source profile that is itself a role) with
     cycle detection;
   - `role_arn` + `credential_source` -> `AssumeRole` from Environment / Ec2InstanceMetadata /
     EcsContainer credentials;
   - `AWS_ROLE_ARN` + `AWS_WEB_IDENTITY_TOKEN_FILE` (env form of IRSA) ->
     `AssumeRoleWithWebIdentity`;
   - `web_identity_token_file` (+ `role_arn`) -> STS `AssumeRoleWithWebIdentity` (IRSA);
   - regional STS endpoints by default, honoring `AWS_STS_REGIONAL_ENDPOINTS`;
   - `sso_session` / `sso_start_url` + `sso_account_id` + `sso_role_name` -> read
     `~/.aws/sso/cache/*.json`, call `sso:GetRoleCredentials`;
   - `credential_source` = Environment / Ec2InstanceMetadata / EcsContainer.
3. IMDSv2 (`http://169.254.169.254`, token + role name + creds), short timeouts, no proxy.
4. ECS container credentials (`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` / `_FULL_URI`).
5. Error text mirrors botocore where cheap ("Unable to locate credentials"), because krikri's output
   parity bar includes error text.

SSO details: cache-file naming must match botocore exactly for `sso_session` blocks
(sha1-hex of the session name / start URL). Pin it with a test using a temp cache dir. Expired SSO
tokens cannot be refreshed without the CLI; fail with `The SSO session associated with this profile
has expired or is invalid. Please run aws sso login` (parity text). Native SSO does **not** require
the AWS CLI; the `aws-sso-util` example under `credential_process` is an alternative route, not the
supported one, and both coexist in the chain.

MFA (`mfa_serial`): **deferred** to a follow-up, not a v1 blocker (decided 2026-11-21). The
credential chain already isolates providers, so adding a TTY-prompt provider (GetSessionToken /
AssumeRole with `SerialNumber`+`TokenCode`) is a contained change. v1 fails with the parity error
(`Enter MFA code for ...` / "MFA required") and a pointer that MFA profiles are not yet supported;
track it as its own GitHub issue and in `KNOWN_MISSING.md`.

`credential_process`: supported (it is standard AWS SDK behavior and boto3-based Ansible users rely
on it). Examples to document:

```ini
# ~/.aws/config
[profile ssm-test]
credential_process = /usr/bin/aws configure export-credentials --profile ssm-test --format process

[profile sso-test]
credential_process = /usr/local/bin/aws-sso-util credential-process --profile sso-test
```

The contract is the SDK's: the command prints JSON
`{"Version":1,"AccessKeyId":...,"SecretAccessKey":...,"SessionToken":...,"Expiration":...}`
to stdout and krikri re-runs it near expiry. Document that it executes a configured command.

AssumeRole is **in scope for v1** (explicitly requested): profile-based assume-role, source-profile
chains, `credential_source`, external ID, session name/duration, IRSA. Only the **MFA-token variant**
of AssumeRole (`mfa_serial`) is deferred (section 5.4). The live suite must cover a real
`role_arn`+`source_profile` profile, so phase 0 creates a test role (section 13).

### 5.5 KMS session encryption

Agent requests `KMSEncryption` with `KMSKeyId` only when the account's Session Manager preferences
mandate encryption; unsupported -> sessions in those accounts fail, so it is in scope.

Exchange (from the bridge's protocol doc + plugin `encryption/`):

1. Agent `HandshakeRequest` action `KMSEncryption` with `{KMSKeyId}`.
2. Client calls KMS `GenerateDataKey` (`KeyId`, `NumberOfBytes: 64`, encryption context
   `{"aws:ssm:SessionId":..., "aws:ssm:TargetId":...}`); returns plaintext 64-byte key + ciphertext.
3. `HandshakeResponse` action result must mirror the plugin's JSON byte-for-byte:
   `{"KMSCipherTextKey": <base64 of ciphertext blob>, "KMSCipherTextHash": null}`. Both fields are
   declared `[]byte` in `handshakemessage.go`; the plugin sets only the key, so the hash marshals as
   `null`. Emitting only the key may pass or fail depending on an agent-side check we cannot see -
   pin the exact shape (base64 string + null) and test it.
4. Agent `EncChallengeRequest` (payload type 8) -> client `EncChallengeResponse` (type 9). The field
   is `Challenge` (**base64** of the Go `[]byte`) in both directions - not `ChallengeEnc`. The
   response is produced by decrypting the challenge with the inbound key and re-encrypting it with
   the outbound key (plugin `handleEncryptionChallengeRequest`). Pin that transform and the full JSON
   of all four handshake payloads (including `HandshakeResponsePayload.Errors`).
5. From then on: AES-256-GCM, first 32 bytes of the plaintext key decrypt inbound, last 32 encrypt
   outbound (agent mirrors), 12-byte random nonce prepended to ciphertext, per message.
   Encrypted payload types: 1, 11, 12 only.
6. Missing KMS permissions -> fail the handshake with an explicit error, never downgrade to plaintext.

Crystal: `OpenSSL::Cipher#gcm_tag` / `#gcm_tag=`; pin encrypt/decrypt with OpenSSL-CLI-derived
vectors (independent implementation) plus a round-trip test.

### 5.6 Client (control plane)

- `aws_json` helper: POST, `Content-Type: application/x-amz-json-1.1`, `X-Amz-Target:
  AmazonSSM.<Action>`, Host header, `krikri-aws-signer`, endpoint override support.
- Actions: `StartSession`, `ResumeSession` (same session/process after a drop), `TerminateSession`.
- Map `TargetNotConnected`, `AccessDeniedException`, `InvalidDocument`, `SessionNotFound`,
  throttling to typed errors with the API's own message text.
- Retry policy: connection-establishment retries only (`Settings.retries`, exponential backoff with
  jitter); never retry a command that may have run.
- `TerminateSession` on `Session#terminate`, `at_exit` safety net, and on clean krikri shutdown.
- Session lifetime: Standard sessions idle-timeout/cap per account preferences (default 20 min idle,
  1 hour max). The shard surfaces `ChannelClosed` output text; krikri decides resume-vs-fail.

### 5.7 Shard tests

Unit (no network):
- codec: header layout, message/payload type strings, digest verify/reject, zero-length exemption,
  UUID byte order both ways (hand-written expected bytes);
- handshake JSON: exact field names, `SessionType` rejection path, base64 `[]byte` fields;
- reliability: sequence allocation under concurrency (one number issued exactly once), in-order/gap/
  duplicate handling, retransmit only head, RTO math with a fake clock;
- credentials: env precedence, profile INI parsing (incl. `sso_session`, `credential_process`,
  `role_arn` chain), SSO cache naming/expiry, IMDSv2 request/response with a local HTTP server,
  ECS, web identity; all with a transport seam rather than real AWS;
- KMS: GenerateDataKey request shape, base64 encoding + `KMSCipherTextHash: null`, challenge
  decrypt->re-encrypt transform, GCM vectors, nonce handling;
- client: StartSession request/response/error mapping against a local HTTP endpoint, endpoint-url
  override, retries.

Integration (in-process fake SSM, no AWS), harness under `src/krikri_aws_ssm/testing/`:
- `fake_gateway.cr`: `HTTP::Server` serving `StartSession`/`ResumeSession`/`TerminateSession` JSON
  and a websocket endpoint that speaks the real framing. It **verifies SigV4** with known test
  credentials and asserts the exact signed-header set and Host value of the upgrade - the cheapest
  detector for the Host/port and signing-order class of bug.
- `fake_agent.cr`: handshake (with and without KMS), start_publication, output streaming,
  acks/retransmit exercises, channel_closed, exit-code payload.
- `pty.cr`: `LibC.openpty` binding; the fake agent attaches `/bin/sh` to the slave side, so pty
  semantics (CR/LF, echo, canonical line limits) are exercised for real.
- Scenarios: exec a command, 1MB and ~40MB-scale (compressed) transfers both ways with the ack queue
  and `pause_publication` backpressure under load, interleaved stdout/stderr, abrupt socket close ->
  reconnect via `ResumeSession`, KMS handshake end to end with a fake KMS action.
- Conformance target in the `justfile`: run the real `session-manager-plugin` and `krikri-aws-ssm`
  against the same fake agent and diff the byte streams (skipped when the plugin is absent).

### 6.3 Transport dispatch seam

Files: `src/krikri/ssh_manager.cr`, new `src/krikri/ssm_transport.cr`, new `src/krikri/ssm_registry.cr`.

- The transport is decided from the **resolved connection type** everywhere, not from "a session
  exists": the same `SSM_CONNECTION_TYPES` predicate that `connection_plugin_transport` uses also
  gates `daemon_unavailable?`, rsync, control sockets and ssh args. A lazily-created session must
  never be what makes a host SSM, or `try_daemon_batch` (`executor_run_loop.cr:2413`) will take the
  SSH daemon path before registration.
- `SsmRegistry` (mutex-protected) maps the exact dispatch tuple the entry points already receive
  (`host`, plus the resolved `SsmSettings` key) to a lazily created `KrikriAwsSsm::Session`. Two
  inventory names for one instance and task-level `ansible_connection` flips must not alias one
  session with different settings.
- Delegate at the transport entry points only: `exec` (`ssh_manager.cr:468`), `exec_script` (`:554`),
  `upload` (`:1178`), `download` (`:1232`). `rsync_upload*` returns false for SSM hosts so
  `upload_plugins_to_host` (`plugin_manager.cr:1253-1280`) falls back to `upload`.
- Lifecycle parity: `reset_connection` (`ssh_manager.cr:1126`, from `meta: reset_connection` at
  `executor_display_misc.cr:1771`) terminates and drops the session; `close_connection` (`:1418`)
  and `close_all_daemons` (`:1153`) behave like their SSH counterparts; `close_all` (`:1439`)
  terminates everything, plus a bounded `at_exit` safety net.
- Staging identity: `remote_plugin_dir` (`plugin_manager.cr:63-65`) tags `/var/tmp` by `conn.user`,
  but under SSM the writer is the session OS user (`ssm-user`). Tag SSM staging by the session
  identity (or use a per-run 0700 dir) so a later SSH run cannot hit ownership conflicts, and route
  the chown probes (`plugin_manager.cr:1736/1768`) through the same become wrapper.

### 6.4 Shell protocol (krikri-side)

`SsmTransport` drives one serialized shell per session:

- Boot: wait for the first prompt/handshake complete, then `stty -echo; unset PROMPT_COMMAND;
  PS1=''; export TERM=dumb; stty -onlcr` (validate; CR handling chosen after fake-agent + live tests),
  and a sentinel command to flush any banner before the first real command.
- `exec(command)` -> `printf '%s\n' <begin>; /bin/bash -c <quoted command>; printf '\n%s\n%s\n'
  "$?" <end>` between markers; discard everything before `<begin>`; split stdout from the exit code;
  stderr arrives on payload type 11 (kept separate).
- `exec_script(script)` -> stream the script as base64 through the pty into
  `head -c <b64_len> | base64 -d | bash`, with one begin marker before and one end marker after.
  This preserves krikri's existing secret invariant (the become password lives in the script text,
  never in argv or on remote disk: see `plugin_manager.cr:2714` and the `exec_script`-only rule at
  `plugin_manager.cr:2794`). `head -c` gives a deterministic EOF without relying on pty `^D`.
  Secret-free scripts may use a temp file only as a performance fallback, never when the text
  contains a password.
- Type the command itself in pty-safe pieces: a single wrapped command line longer than Linux
  `MAX_CANON` (4096) is silently truncated by the line discipline. Above a conservative threshold
  (~3500 chars) run the command through the same `head -c | base64 -d | bash` bootstrap (or a
  backslash-continued multi-line command), and add an 8KB-command fake-pty test.
- Timeouts: per-command deadline; on expiry terminate the session and report the command as timed
  out (krikri's SSH `DEFAULT_EXEC_TIMEOUT_SECONDS` semantics), no retry of the command.
- Session loss mid-command: fail the task with the transport error; do not re-run (unknown state),
  matching krikri's `DaemonDispatchUnknownError` philosophy. `ResumeSession` is used only when no
  command is in flight.

### 6.5 Transfers

- Upload (destination files only, including the 40MB fat plugin binary):
  `head -c <b64_len> | base64 -d | <decompressor> > <dest>` and stream base64 lines
  (<=3000 chars per write; pty canonical input line limit is 4096) into the shell's stdin; one
  begin marker before, one end marker after. `head -c` gives a deterministic EOF without ^D.
  Compression: prefer `xz -dc` if present, else `gzip -dc`, else raw (chosen once per session with a
  probe). Then `chmod`/`mv` into place with the atomic-rename semantics the SSH `upload` has.
- Download: `base64 < <src>` between markers, parse lines until the end marker (strip `\r`), decode.
  Optional `gzip` on the target when requested by the caller.
- 40MB fat plugin binary per host: measure. Expect xz ~12MB compressed -> ~16MB base64; log a
  timing line under `--verbose` and document the cost. Transfer is once per host per run thanks to
  the existing md5 remote-cache logic (`plugin_manager.cr:1200-1330`).

### 6.6 become / async / delegate / check / diff / batch

- `become`: shell-level (`sudo -n` / `sudo -S -p ''`), but **not** "works unchanged": Ansible's
  aws_ssm sets `_play_context.remote_user = getpass.getuser()` (`aws_ssm.py:536`), i.e. the
  controller username, not `ansible_user`, and the real OS identity is the session user. krikri's
  `become_needed?` decisions (`plugin_manager.cr:2695`, `executor_run_loop.cr:2385`,
  `plugin_manager.cr:1736/1768`) must be fed the same baseline Ansible uses for this connection, or
  become/non-become results diverge. Verify real ansible's become wrap once (bucket-enabled host)
  and test `become: true` with/without `become_user`, with `ansible_user` set/unset, and with an
  `ssm_document` using `runAsEnabled`/`runAsDefaultUser`.
- `delegate_to`: resolved host goes through the same `ConnectionSettings` path; an SSM host delegated
  to runs over SSM, a local/inventory host runs as today.
- check mode / diff: engine-level, no transport work. Verify via integration tests.
- async: **not supported in v1** (decided 2026-11-21). An `async:` task on an SSM host fails
  cleanly with a clear message (`async is not supported over aws_ssm yet`) instead of half-working.
  The reason is concrete: the existing launch is `nohup ... &` with no stdin redirect, so over a pty
  the background job would steal the bytes of the next command; making it correct needs `</dev/null`
  plus `setsid` and a live check of whether the agent reaps detached children on session close.
  Track as its own follow-up issue (estimated 1-1.5d, no architectural change), and document the
  limitation in `KNOWN_MISSING.md`.
- batching: script path only (daemon off for SSM). Multiple steps still share one session and one
  script round trip, so batching keeps its benefit minus the daemon.
- gather_facts, loops, handlers: no transport changes; covered by integration tests.

  (SSM-only, which is the point of the feature).
- Secret hygiene for the live suite: credentials reach the shard through the standard chain (env or a
  temporary profile file under a 0700 dir), never through the repo, and the test logs redact account
  id, session id and token.
